# University Internship Platform

سامانه سبک و یکپارچه مدیریت عملیات کارآموزی دانشگاه؛ با تمرکز بر **تخصیص فعالیت، اجرای قابل‌پیگیری، تأیید تحویل و ثبت دقیق ساعت کارآموزان**.

> این README بر اساس سند `docs/product/product-blueprint.md` بازنویسی شده است. سند Product Blueprint مرجع اصلی تصمیم‌های محصول است. فناوری‌های Backend و PWA هنوز انتخاب نشده‌اند؛ بنابراین مخزن مستقل از فریم‌ورک باقی مانده است.

## تعریف محصول

در هر لحظه باید بتوان پاسخ داد: **چه کسی، چه کاری، کجا، تا چه زمانی، با چه شواهدی انجام می‌دهد و چند ساعت کار ثبت و تأیید کرده است؟**

سه هسته اصلی محصول:

1. **تخصیص کار:** قالب‌های رسمی قابل استفاده مجدد و تسک سریع سرپرست.
2. **اجرا و بررسی:** کارآموز فعالیت را تحویل می‌دهد و سرپرست نتیجه را بررسی می‌کند.
3. **ثبت ساعت:** کارآموز ورود و خروج را ثبت می‌کند و سرپرست ساعت‌ها را هفتگی تأیید می‌کند.

این محصول در نسخه اول نرم‌افزار ارزیابی مهارت، HR پیچیده یا ابزار ردیابی مکانی نیست.

## مقیاس و پلتفرم

- مقیاس هدف فعلی: حداکثر **۲۰۰ کاربر**.
- تجربه کاربری: **PWA**؛ موبایل‌محور برای کارآموز و واکنش‌گرا برای سرپرست و ادمین.
- در MVP ردیابی دائمی GPS و نقشه گرافیکی دانشگاه وجود ندارد.
- فناوری Backend و PWA هنوز انتخاب نشده‌اند و باید در ADR ثبت شوند.

## نقش‌ها و دامنه دسترسی

| نقش | دامنه | مسئولیت اصلی |
|---|---|---|
| کارآموز (`intern`) | اطلاعات و فعالیت‌های خودش | اجرا، تحویل، ثبت ورود و خروج |
| سرپرست (`supervisor`) | کارآموزان تحت مسئولیت فعلی و جانشینی فعال | تخصیص، بررسی تحویل، تأیید ساعت هفتگی |
| ادمین (`admin`) | یک یا چند دانشکده، یا کل دانشگاه | کاربران، دوره‌ها، مکان‌ها، قالب‌ها، گزارش‌ها و مداخله‌های مدیریتی |

**نقش رهبر وجود ندارد.** دسترسی سراسری با همان نقش ادمین و Scope برابر `global` پیاده‌سازی می‌شود. ادمین دانشکده Scope محدود به دانشکده‌های مجاز دارد. یک کاربر می‌تواند بیش از یک نقش یا Scope داشته باشد.

## تصمیم‌های کلیدی محصول

- هر کارآموز در هر بازه زمانی فقط یک سرپرست اصلی فعال دارد؛ رابطه‌های قبلی با تاریخ شروع و پایان حفظ می‌شوند.
- قالب رسمی تسک را ادمین می‌سازد؛ سرپرست می‌تواند **تسک سریع** بسازد.
- تخصیص می‌تواند برای کارآموز، مسئولیت شخصی سرپرست یا توزیع به کارآموزان باشد.
- تسک گروهی یک تسک با چند Assignment مستقل است.
- مکان فعالیت حضوری، آنلاین یا بدون مکان ثابت است.
- تحویل کارآموز مرحله اول تأیید است؛ سرپرست نتیجه را بررسی و نهایی می‌کند. مرحله تأیید جداگانه‌ای برای کارآموز ایجاد نمی‌شود.
- خروجی بررسی سرپرست می‌تواند تأیید، بازگشت برای اصلاح یا رد نهایی باشد.
- ثبت ساعت مستقل از تسک‌ها و با نشست ورود/خروج انجام می‌شود.
- ساعت‌ها به‌صورت هفتگی توسط سرپرست تأیید می‌شوند.
- تعویق با درخواست کارآموز و تصمیم سرپرست انجام می‌شود.
- تغییر سرپرست یا خروج کارآموز باعث حذف سوابق یا لغو خودکار تسک‌های باز نمی‌شود.
- هر مداخله حساس ادمین باید دلیل و Audit Log داشته باشد.

جزئیات کامل در [`docs/product/product-blueprint.md`](docs/product/product-blueprint.md) آمده است.

## شروع کار

### ۱. ایجاد Repository

در GitHub یک Repository با نام `university-internship-platform` و سطح دسترسی **Private** بسازید. هنگام ساخت، گزینه ایجاد README، `.gitignore` یا License را فعال نکنید؛ فایل‌های این بسته از قبل آماده‌اند.

### ۲. Push اولیه

```bash
git init
git add .
git commit -m "chore: initialize internship platform repository"
git branch -M main
git remote add origin https://github.com/<GITHUB_OWNER>/university-internship-platform.git
git push -u origin main
```

`<GITHUB_OWNER>` را با نام حساب یا سازمان GitHub جایگزین کنید.

### ۳. محافظت از شاخه اصلی

در GitHub برای `main` یک Ruleset یا Branch Protection بسازید:

- Push مستقیم به `main` ممنوع باشد.
- Merge فقط از طریق Pull Request انجام شود.
- Workflow اعتبارسنجی باید موفق باشد.
- دسترسی Write، Admin و مدیریت Secrets فقط به افراد لازم داده شود.

## گردش توسعه

- هر کار جدید باید Issue داشته باشد.
- هر تغییر در Branch مستقل توسعه داده شود.
- تغییرات با Pull Request وارد `main` شوند.
- تغییر رفتار محصول باید مستندات محصول را هم به‌روز کند.
- تغییر معماری یا فناوری باید ADR داشته باشد.
- قواعد کامل در [`CONTRIBUTING.md`](CONTRIBUTING.md) است.

## CI/CD و انتشار

| Workflow | رویداد | مسئولیت |
|---|---|---|
| `validate-repository.yml` | Pull Request و Push | اعتبارسنجی ساختار، مستندات و فایل‌های ضروری |
| `publish-container-images.yml` | Push به main یا Tag نسخه | Build و Push ایمیج‌های `api` و `pwa` به GHCR؛ فقط وقتی Dockerfile وجود داشته باشد |
| `deploy-production.yml` | اجرای دستی | اتصال SSH به سرور، Pull ایمیج انتخاب‌شده و اجرای Docker Compose |

تا زمان انتخاب فناوری‌ها و اضافه‌شدن Dockerfile واقعی برای `apps/api` و `apps/pwa`، انتشار Container عمداً انجام نمی‌شود. Workflow در این وضعیت به‌صورت موفق با پیام Skip تمام می‌شود.

نام ایمیج‌ها:

```text
ghcr.io/<owner>/university-internship-platform-api:<tag>
ghcr.io/<owner>/university-internship-platform-pwa:<tag>
```

پیش‌نیازهای GHCR، Secrets و سرور در [`docs/operations/deployment.md`](docs/operations/deployment.md) توضیح داده شده‌اند.

## امنیت و داده

- `.env`، توکن، رمز، کلید خصوصی و داده واقعی دانشجویان را Commit نکنید.
- `.env.example` فقط نام متغیرها و مقادیر نمونه غیرحساس دارد.
- برای انتشار از GitHub Secrets و Environment Secrets استفاده کنید.
- مجوز دسترسی باید در Backend و بر اساس Role و Scope بررسی شود؛ مخفی کردن دکمه در UI کافی نیست.
- اصلاح ساعت، تغییر سرپرست و مداخله روی تسک نهایی باید دلیل و Audit Log داشته باشد.
- رخدادهای امنیتی را طبق `SECURITY.md` گزارش کنید.
